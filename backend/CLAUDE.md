# Backend ОКО — Spring Boot

Зона: Данил. Контракт: `../contracts/oko-openapi.yaml`. Схема: `../docs/db.md`, переносится в Flyway `V1__init.sql`.

Стек из `docs/architecture.md`: Spring Boot 3, Spring Security, Spring Data JPA, Flyway, PostgreSQL. Версии Java и PostgreSQL, систему сборки (Maven или Gradle) и тестовые библиотеки фиксирует Данил в первом коммите каркаса. До этого этот файл дополняется.

## Структура пакетов

Модули по `architecture.md`, раздел 3:

```
app/
├── auth/          вход, сессия, роли, IdentityProvider (sso/, stub/)
├── catalog/       продукты, сервисы, владельцы, ключи, allowed_origin, widget_settings
├── ratings/       приём оценок — самый важный модуль
├── stats/         агрегаты, сводка, динамика, лента
├── releases/      метки релизов, окна до/после
├── monitoring/    MonitoringSource, опрос, service_status
├── widget/        настройки виджета, frame-страница, health для «загружался»
└── common/        ошибки, безопасность, время, конфиг
```

В каждом модуле: `api` (контроллеры и DTO), `service`, `repo`.

Правила зависимостей:
- `ratings` не импортирует `monitoring`. `stats` не пишет в `ratings`.
- `api` не обращается к `repo` напрямую, только через `service`.
- SSO и мониторинг — только за интерфейсами `IdentityProvider` и `MonitoringSource`.
- Контроллеры возвращают DTO. JPA-сущности наружу не отдаются.

## Контракт

- Реализуем то, что написано в спецификации: путь, метод, поля, коды ошибок.
- Поля, которых нет в спецификации, в ответ не добавляем. Нужное поле — PR в спецификацию.
- На каждый эндпоинт — тест «ответ проходит схему» из `oko-openapi.yaml`.
- Формат ошибок: `{code, message, details}` на верхнем уровне. `message` — по-русски для человека. Коды — только из enum спецификации.
- Единый `@RestControllerAdvice`. Ошибки валидации — 400 `VALIDATION_ERROR` с `details[]`. Стектрейсы и SQL в ответе не появляются. Внутренняя ошибка — 500 с `requestId` в логе.
- Чужой продукт владельцу — `404 NOT_FOUND`, не `403`. Так не раскрываем, что продукт существует.

## Безопасность — обязательно

**Вход и сессия**
- При `/auth/callback` проверяй `state`. Без проверки вход считается недействительным.
- `returnTo` — только относительный путь, начинающийся с `/` и не с `//`. Иначе открытый редирект.
- Обмен `code` на токен не логируем: URL содержит `client_secret`. Если SSO принимает POST, используем POST.
- Cookie `OKO_SESSION`: `HttpOnly`, `Secure`, `SameSite=Lax`.
- Изменяющие запросы панели защищены CSRF-токеном (`X-XSRF-TOKEN`).

**Ключи**
- Генерация через `SecureRandom`, не менее 256 бит. Префиксы `pk_` (публичный) и `sk_` (секретный).
- В БД хранится только SHA-256 (`key_hash`). Для случайных 256-битных ключей этого достаточно.
- Полный ключ показывается один раз, в списке — только `keyPrefix`.
- Отозванный ключ перестаёт работать сразу: проверка `revoked_at` на каждом запросе, без кэша.
- Публичный ключ не принимается на секретных эндпоинтах и наоборот (`401`).

**Оценивающие**
- `raterId` от виджета и сервера никогда не хранится в открытом виде: `rater_hash = HMAC-SHA256(secret, raterId)`.
- HMAC-секрет — из переменной окружения. Его смена делает старые хэши несравнимыми, это нужно учитывать при ротации.
- Сравнение хэшей вручную — через `MessageDigest.isEqual`.

**Виджет и встраивание**
- `Origin` — не аутентификация: его подделывает любой скрипт вне браузера. Защита строится на трёх вещах: ключ, лимиты (по ключу и по IP, IP мягкий), `frame-ancestors`.
- `frame-ancestors` строится из `allowed_origin` продукта. Пустой список — `frame-ancestors 'none'`.
- Формат origin проверяется строго: схема, хост, необязательный порт. Без `*`, без пути, без завершающего `/`.
- Настройки виджета (`/widget/config`) и ответы с ключами — `Cache-Control: no-store`.
- Все JSON-ответы — `application/json`, плюс `X-Content-Type-Options: nosniff`.

**Данные и внешние запросы**
- URL продуктов и сервисов мы сохраняем, но сами по ним не ходим. Это защита от SSRF. Доступность проверяет только мониторинг.
- SQL — только параметризованный. Сортировка и поля фильтра — по белому списку.
- Админы берутся из конфигурации (переменная окружения). Пустой список означает, что админов нет. Роль из запроса не принимается.
- Заглушка SSO включается только профилем `dev`. Тест на старте: в `prod` заглушка не регистрируется.
- Тексты оценок, `comment`, `raterId`, тела запросов `/ratings`, `/widget/ratings`, `/auth/callback` в логи не пишем.
- Лимит тела запроса — 16 КБ. Длина `comment` ограничена 500 символами.

## Приём оценок — самое важное

Порядок проверок — как в спецификации: ключ существует и активен → продукт активен → `Origin` (только виджет) → лимиты → формат и длина → `serviceId` принадлежит продукту → дубликат за 14 дней.

Транзакция:
1. `pg_advisory_xact_lock` по паре `(product_id, rater_hash)`. Без него два параллельных запроса одного человека оба пройдут проверку дубликата. Индекс `rating_dedup_idx` не уникальный и от этого не защищает.
2. Проверка дубликата по `rating_dedup_idx`.
3. Вставка в `rating`.
4. Upsert в `rating_daily`: строка `(product_id, 0, day)` всегда и строка `(product_id, service_id, day)`, если сервис указан. `day` — дата в зоне `Asia/Tomsk` от `created_at`.
5. Коммит. Ответ `201 {id}`.

Ошибка на любом шаге откатывает всё. Агрегаты не расходятся с `rating`.

Внутри транзакции не вызываем SSO, мониторинг и никакие внешние сервисы.

Лимиты запросов в памяти приложения (MVP, один сервер). Ответ `429` с `Retry-After`.

## Агрегаты и статистика

- Средняя = `sum_score / cnt`, округление до одного знака на выходе. В БД не хранится.
- Индекс = `(c4 + c5) / cnt × 100 − (c1 + c2) / cnt × 100`, округление до одного знака.
- Гистограмма всегда из пяти элементов, даже если часть оценок равна нулю.
- `lowSample = cnt < 20`.
- Пустой период: `average = null`, `index = null`, `count = 0`.
- Недели — с понедельника, месяцы — календарные, всё по зоне Томска.
- Сверка: сумма по `rating` за период равна сумме по `rating_daily`. Это отдельный тест.

## Релизы и до/после

- Окно «до»: 14 дней перед днём релиза, не раньше даты предыдущего релиза того же продукта (или сервиса). Если обрезано, в ответе `clippedByReleaseId`.
- Окно «после»: 14 дней, начиная с дня релиза, не позже даты следующего релиза.
- Окна считаются на лету из `rating_daily`. Дата релиза переводится в день по Томску.
- Пустое окно: `average = null`, `averageDelta = null`.

## Владельцы, архивация, уникальность

- Минимум один владелец. Удаление и понижение владельца выполняются в транзакции с `SELECT ... FOR UPDATE` по строке `product`. Без блокировки два параллельных удаления могут оставить продукт без владельца. Нарушение правила — `409 LAST_OWNER`.
- Добавить владельца можно только того, кто уже есть в `app_user`. Иначе `404`.
- Архивация — только для админа, проверка по роли. Повторный вызов — `204`. Ключи отзываются, виджет отключается.
- URL уникален среди неархивных продуктов без учёта регистра. Проверяем до вставки, а нарушение индекса ловим и отдаём `409 DUPLICATE_URL`, не `500`.

## Миграции и БД

- Схема меняется только Flyway. Применённую миграцию не правим, добавляем новую `V{n+1}`.
- Колонки `rating_daily` — как в `docs/db.md`: `cnt`, `sum_score`. В спецификации и контракте написано `count` и `sum`. До решения Данила и Николая используем `db.md`.
- `app_user.is_admin` из `db.md` не используем: админы задаются конфигом.
- Enum в PostgreSQL не создаём. Используем `text` с `CHECK`.

## Тесты — обязательно

Юнит-тесты:
- подсчёт среднего, индекса, гистограммы, `lowSample`;
- окна до/после с обрезкой с обеих сторон;
- HMAC, проверка формата origin, валидация полей.

Интеграционные (Testcontainers, настоящий PostgreSQL):
- приём оценки: успех; неверный ключ; отозванный ключ; архивный продукт; чужой `Origin`; дубликат; два параллельных запроса одного человека; текст длиннее 500; `serviceId` чужого продукта;
- права: владелец не видит чужой продукт (`404`); последний владелец (`409`); архивация не админом (`403`);
- сверка `rating` и `rating_daily`;
- контрактные тесты по `oko-openapi.yaml`;
- отказы: БД недоступна — `503`; мониторинг недоступен — статус «нет данных», остальное работает.

Перед «готово»: сборка и тесты в `backend/` зелёные. Ответы сверены со спецификацией.
