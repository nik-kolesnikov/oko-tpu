# Интеграция мониторинга ТПУ с ОКО

Актуально для ветки `feat/monitoring-integration`. Основано на [проекте контракта команды мониторинга](https://github.com/oliivvs/monitoring_resources_tpu-/blob/58bf529/doc.md) от 08.11.2026. Этот файл можно передать команде мониторинга целиком; секреты в него не вписывать.

## 1. Что уже можно подключить

ОКО принимает события `STATUS_CHANGED` и `HEARTBEAT` по HTTPS:

```
POST https://<домен-ОКО>/api/v1/status/events
Authorization: Bearer <EVENT_TOKEN>
Content-Type: application/json
```

Точный домен ОКО сообщит владелец VPS. Порт снаружи — **443**. Домен должен разрешаться с машины отправителя и иметь действующий TLS-сертификат. В ОКО Caddy принимает HTTPS, nginx направляет `/api/` в backend. IP VPS нужен только если у отправителя есть отдельный сетевой список разрешённых адресов; для настройки `MONITORING_EVENT_POST_URL` достаточно домена.

Есть **другой** список разрешённых адресов: адреса ресурсов, которые сам мониторинг вправе проверять. В этот список добавляют домен/порт *проверяемого сервиса*. Домен ОКО добавляют туда лишь если мониторинг действительно будет проверять доступность ОКО как ресурса. Для доставки событий нужен исходящий HTTPS-доступ от мониторинга к ОКО.

### Настройки по сторонам

| Где | Переменная | Значение |
|---|---|---|
| VPS ОКО, `/opt/oko/.env` | `OKO_MONITORING_EVENT_TOKEN` | Длинный случайный секрет; не пустой |
| Мониторинг, окружение sender | `MONITORING_EVENT_POST_URL` | `https://<домен-ОКО>/api/v1/status/events` |
| Мониторинг, окружение sender | `MONITORING_EVENT_TOKEN` | Тот же секрет |

Генерация на доверенной машине: `openssl rand -hex 32`. Передайте секрет через защищённый канал. Коммитить его, вставлять в PR или чат с публичным доступом нельзя. После задания переменной пересоздайте backend-контейнер, чтобы он прочитал её; миграцию БД Flyway выполнит при запуске. Если переменная пуста, endpoint отвечает `503` и отправитель должен повторить доставку позднее.

В текущем `compose.yaml` мониторинга sender направлен на Mock API. При совместном запуске замените его URL и токен на значения выше. Не требуется ставить оба проекта в одну Docker-сеть: связь идёт через публичный HTTPS.

## 2. Привязка ресурсов

Один `resource_id` мониторинга соответствует одной проверяемой службе и одному типу проверки. В панели ОКО создайте сервис внутри нужного продукта и запишите **точно тот же** идентификатор в поле `monitoringRef`. Он уникален во всём ОКО; регистр и символы имеют значение. Например, `portal-http` и `portal-tcp` — разные ресурсы и, если нужны обе проверки, два сервиса ОКО.

ОКО принимает событие даже до создания сервиса (`202`) и сохраняет его в БД без привязки. При создании сервиса или назначении `monitoringRef` ранее полученные события применяются в порядке времени проверки. Неизвестные ресурсы не появляются автоматически в каталоге: команда ОКО должна решить, к какому продукту их привязать.

При смене `monitoringRef` у сервиса текущая лампочка сбрасывается до получения данных для нового идентификатора. История старого идентификатора остаётся в журнале событий и не переносится автоматически на новый сервис.

## 3. Формат события

Все девять полей обязательны; `response_time_ms` и `error` могут иметь значение `null`:

```json
{
  "event_id": "37253074-ee80-437b-9aa1-5344fd057956",
  "event_type": "STATUS_CHANGED",
  "resource_id": "portal-http",
  "resource_name": "Портал ТПУ — HTTPS",
  "status": "DOWN",
  "check_type": "HTTP",
  "checked_at": "2026-11-08T14:12:11.136294Z",
  "response_time_ms": 31.644,
  "error": "ConnectionError"
}
```

`event_type`: `STATUS_CHANGED` или `HEARTBEAT`; `status`: `UP`, `DOWN`, `UNKNOWN`; `check_type`: `HTTP`, `TCP`. `checked_at` — UTC-время **проверки**, а не отправки. Для `response_time_ms` допустимо неотрицательное число или `null`; ОКО округляет его до целой миллисекунды по правилу half-up. Событие не должно превышать 16 КБ, `resource_id` — 255 символов, `resource_name` — 500, `error` — 4096. Ошибку лучше ограничить ещё короче: nginx превращает превышение лимита тела в `400`, а sender считает все `4xx`, кроме `429`, окончательной ошибкой. Текст `error` сохраняется в журнале, но не показывается пользователю.

### Ответы и повторная доставка

| Код | Тело / действие sender |
|---|---|
| `202` | `{"event_id":"...","result":"accepted"}` — новое событие сохранено; пометить `SENT` |
| `200` | `{"event_id":"...","result":"duplicate"}` — тот же `event_id` и те же данные; пометить `SENT` |
| `409` | `event_id` уже использован с иным содержимым; исправить источник, автоматический повтор бесполезен |
| `400` | Исправить формат/размер; автоматический повтор бесполезен |
| `401` | Проверить токен; после исправления вручную переотправить неудавшиеся события |
| `429` | Повторить после `Retry-After`, если когда-либо включим лимит |
| `503`, другие `5xx`, таймаут | Сохранить в outbox и повторять с задержкой |

ОКО сохраняет `event_id` и содержимое в PostgreSQL в одной транзакции с обновлением состояния. Автоматической очистки журнала пока нет: так повтор после длительного простоя остаётся идемпотентным. Дубликат не добавляет запись в историю статусов. Событие со старым `checked_at` сохраняется и подтверждается, но не перезаписывает более новое состояние. При равных `checked_at` `STATUS_CHANGED` имеет приоритет перед `HEARTBEAT`; события одного типа с одинаковой меткой времени не должны противоречить друг другу.

## 4. Свежесть и лампочки

ОКО отображает `UP` как зелёный, `DOWN` как красный; для продукта с разными сервисами возможна жёлтая лампочка. `UNKNOWN`, отсутствие данных или последняя проверка старше **5 минут** дают серую лампочку. Повторно пришедший `HEARTBEAT` с прежним `checked_at` **не продлевает** свежесть проверки. Это важно: свежесть связи и свежесть самой проверки — разные вещи.

Команде мониторинга нужно подключить автоматическую генерацию HEARTBEAT, которая в их `doc.md` пока отмечена как незавершённая. Рекомендуемый интервал для демо — **60–90 секунд**, если сам ресурс проверяется хотя бы раз в 1–2 минуты. Предложенные ими 300 секунд совпадают с порогом устаревания ОКО и могут давать краткие серые лампочки из-за задержки сети/расписания. Если мониторинг может гарантировать новый `checked_at` только раз в 5 минут, порог ОКО придётся отдельно поднять до 10–15 минут (конфигурация `oko.monitoring.stale-after`) после согласования с командой продукта.

## 5. Совместная проверка перед демо

1. Назначить один тестовый `resource_id` и зарегистрировать его как `monitoringRef` у сервиса ОКО. Сообщить команде мониторинга проверяемый URL, тип HTTP/TCP, порт и ожидаемые пороги `2` успешных / `3` неуспешных проверки.
2. На VPS ОКО обновить backend-образ и compose, задать `OKO_MONITORING_EVENT_TOKEN`; убедиться, что backend здоров через `docker compose ps` на VPS. Путь `/actuator/health` закрыт снаружи. Секрет сверить без вывода в логи.
3. С хоста мониторинга проверить DNS, TLS и исходящий HTTPS к `https://<домен-ОКО>/api/v1/status/events` (ответ `401` без токена подтверждает достижимость endpoint).
4. Настроить sender на настоящий URL и токен. Отправить переход `UNKNOWN → UP`, затем имитировать `DOWN`, затем восстановить `UP`; проверить лампочки ОКО.
5. Повторить один и тот же `event_id`: ожидается `200`, в журнале состояния нет второй смены. Отправить старое событие с новым ID: ожидается `202`, лампочка остаётся прежней.
6. На время остановить backend ОКО, убедиться, что sender оставил события в outbox; запустить backend и дождаться `SENT`.
7. Отправить `HEARTBEAT`, убедиться, что он не создаёт переход статуса. После прекращения новых проверок и истечения 5 минут лампочка становится серой, не красной.

## 6. Следующий этап: Pull API

Команда мониторинга в своём документе описала `GET /api/v1/statuses?limit=50&offset=0` с отдельным `READ_TOKEN`, но **на 08.11.2026 метод и Bearer-защита внешнего GET ещё не реализованы**. ОКО поэтому не обращается к существующим незащищённым `/api/v1/resources` и `/api/v1/resources/{id}/status`: они раскрывают больше данных и их схема не утверждена для интеграции.

После реализации и утверждения GET команда ОКО добавит загрузку всех страниц при старте и сверку каждые 5 минут. Для каждой записи понадобятся `resource_id`, `status`, `active`, `checked_at` и при наличии `status_changed_at`. Только более новая проверка обновляет состояние; `active=false` отображается как отсутствие актуальных данных. Требуются адрес API, токен чтения, доступность от VPS ОКО и итоговая схема ответа. Push продолжает работать во время сверки. Временная ошибка GET не удаляет ранее полученные данные: они естественно устаревают по `checked_at`.

До появления GET первичное состояние приходит первым `STATUS_CHANGED` либо `HEARTBEAT`; после длительного отключения sender доставляет накопленный outbox. Это рабочий сценарий демо, но **не полная реализация push+pull контракта**. Не объявляйте этап Pull завершённым без совместного теста защищённого GET.

## 7. Что согласовать между командами

- Реальные домены и сетевой маршрут в обе стороны: мониторинг → ОКО для Push; позже ОКО → мониторинг для Pull. IP нужен, только если сетевой экран команды фильтрует по IP.
- Постоянные `resource_id` и соответствие сервисам ОКО; целевые URL/порты проверок отдельно.
- Интервал проверок и HEARTBEAT относительно 5-минутного порога ОКО.
- Способ безопасной передачи и ротации `EVENT_TOKEN`; отдельно будущего `READ_TOKEN`.
- Максимальный размер `error`, итоговая схема GET, правила `active=false`, срок хранения событий и срок гарантированной повторной доставки.

Список выше не требует передачи публичных IP уже сейчас, если хватает домена и открыт исходящий HTTPS. Для пробного события достаточно домена ОКО, тестового `resource_id`, токена и разрешённого целевого адреса проверки.
