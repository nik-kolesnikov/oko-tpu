# Единая авторизация ТПУ — что это меняет для ОКО

Источник: «Документация SSO ТПУ.md» (полная версия, адрес сервиса https://oauth.tpu.ru). Документация содержит внутренние противоречия, они отмечены ниже.

## Эндпоинты

| Что | Адрес | Метод | Заметки |
|---|---|---|---|
| Авторизация | https://oauth.tpu.ru/authorize | GET | параметры: client_id, redirect_uri, response_type=code, state (обязательно) |
| Обмен code на токен | https://oauth.tpu.ru/access_token | GET | client_id, client_secret, code, state, grant_type, redirect_uri |
| Проверка токена | https://oauth.tpu.ru/check-token | GET | заголовок `Authorization: Bearer <token>` |
| Данные пользователя | https://oauth.tpu.ru/user | GET | заголовок `Authorization: Bearer <token>` |
| Выход | https://oauth.tpu.ru/auth/logout?redirect=<uri> | GET | редирект на наш URI после локального завершения сессии |
| Обновление токена | https://oauth.tpu.ru/access_token | GET | grant_type=refresh_token, refresh_token |

Личный кабинет регистрации приложения — https://api.tpu.ru/dashboard. Там же выдаются api_key, client_id и client_secret, указываются доверенные домены и IP серверов.

## Что важно для ОКО

1. **Регистрация приложения.** Нужны: создание приложения, платформа с версией, OAuth-настройки, доверенные домены, IP всех серверов (включая машины разработчиков при необходимости), проверка приложения ТПУ. Это внешний процесс, он на критическом пути.
2. **client_secret уходит в URL.** Обмен code на токен — GET-запрос, секрет в query-строке. Значит, адрес этого запроса нельзя писать в логи, nginx и прокси тоже должны его маскировать. Проверить, принимает ли SSO POST для этого шага.
3. **Срок жизни токена противоречив.** В разделе «Восстановление» — 30 минут. В разделе про access_token — 24 часа по умолчанию. Уточнить у SSO. Для ОКО это почти не важно: токен нужен один раз, чтобы узнать пользователя, дальше работает наша сессия.
4. **refresh_token живёт неделю.** Нам не нужен: токены ТПУ не храним.
5. **`state` обязателен.** Проверяем его при возврате на `/auth/callback`. Без проверки возможен CSRF-вход.
6. **check-token возвращает user_id, lichnost_id и type.** Тип токена — personal или system. Для нас важен lichnost_id как идентификатор человека (для HMAC оценивающих).
7. **/user не возвращает роль, группу и подразделение.** Есть ID, ФИО, логин и email. Статус студент/сотрудник в ответе не виден, это открытый вопрос к SSO. Если его нет, роль в MVP не собираем.
8. **Персональные токены и системные.** Системные выдаются доверенным приложениям через отложенную авторизацию и с подписью `sig`. Для ОКО они не нужны.
9. **Вход в ОКО через SSO не требует отдельного секрета для пользователя.** Пользователь вводит логин и пароль только на странице ТПУ, мы их не видим. Это соответствует вопросу заказчика 11.

## Исправления в наших документах

- В архитектуре SSO указан как `api.tpu.ru`. Верно: `oauth.tpu.ru`. `api.tpu.ru` — только личный кабинет регистрации. Исправлено в «Архитектура.md».
- В спецификации `oko-openapi.yaml` `/auth/callback` и `/auth/login` описаны без конкретного адреса SSO. Это внутренние эндпоинты ОКО, менять их не нужно, но в описании `/auth/callback` стоит явно указать проверку `state`.
- В «Архитектура.md», раздел 7, и в шаблоне backend `CLAUDE.md` правило «не логировать обмен code» остаётся в силе, потому что секрет в URL подтверждён документацией.

## Открытые вопросы к SSO

1. Какой срок жизни access_token на самом деле: 30 минут или 24 часа?
2. Принимает ли `/access_token` POST вместо GET, чтобы секрет не попадал в URL?
3. Есть ли в `/user` или в другом методе статус студент/сотрудник, группа, подразделение? Какие права нужны приложению на этот метод?
4. Связь `lichnost_id` и `user_id`: может ли у одного человека быть несколько `user_id`?
5. Как выглядит ответ при просроченном или неверном токене (HTTP-код, тело)?
6. Нужна ли отдельная проверка приложения для домена, не относящегося к tpu.ru?
