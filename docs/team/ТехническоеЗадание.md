# Веб-платформа «ОКО ТПУ» (Оценка Качества Объектов ТПУ)

Источник: документ «оценок качества цифровых продуктов ТПУ.docx» из проекта OKO. Текст перенесён без изменений по смыслу. Где ТЗ расходится с решениями встречи, см. «Анализ встречи» и «Вопросы заказчику и ответы».

## Краткое описание проекта

Веб-платформа для централизованной сборки, хранения и визуализации оценок качества цифровых продуктов ТПУ.

## Предпосылки

В экосистеме ТПУ функционирует множество информационных сервисов: личные кабинеты, облачные хранилища, системы электронного обучения, порталы расписания и другие. Однако отсутствует единый инструмент для мониторинга их работоспособности и сбора объективных данных о качестве работы.

В настоящее время оценка состояния сервисов происходит фрагментарно:
- администраторы узнают о проблемах от пользователей из help.tpu.ru;
- нет централизованного хранилища исторических данных о доступности;
- сложно сравнивать надёжность разных сервисов и выявлять системные проблемы;
- отсутствует автоматизированный сбор метрик производительности (время ответа, успешность запросов).

Необходим легковесный, самообслуживаемый инструмент, который позволит:
- любому разработчику легко интегрировать свой сервис через API;
- администраторам видеть сводную картину состояния всех систем;
- ЦЭУ отслеживать метрики своего продукта и реагировать на ухудшения.

## Цели проекта

- Разработка веб-интерфейса для управления продуктами (добавление, редактирование, удаление).
- Генерация уникальных API-ключей для каждого продукта при его регистрации с возможностью смены/отзыва ключа.
- Реализация способа сбора оценок:
  - API-интеграция: отправка оценки через POST-запрос с валидацией API-ключа;
  - встраиваемый виджет: готовый HTML-код для внедрения в веб-интерфейс продукта (оценка от 1 до 5 в виде звёзд или смайлов).
- Создание страницы статистики для каждого продукта с графиками:
  - средняя оценка за день, неделю, месяц, весь период;
  - распределение оценок (гистограмма 1–5);
  - динамика оценок во времени;
  - количество оценок;
  - NPS-подобный индекс: процент положительных оценок (4–5) и отрицательных (1–2).
- Защита от накруток: ограничение частоты отправки оценок с одного устройства или IP, валидация сессий, исключение дубликатов.

## Клиент и ценность

Клиентский сегмент:
- администраторы ЦЭУ — сотрудники, координирующие развитие цифровой экосистемы университета;
- пользователи сервисов — студенты и сотрудники ТПУ (косвенно, через упрощённый интерфейс оценки).

Ценностные предложения для студентов:
- единое окно для мониторинга качества всех цифровых продуктов университета;
- лёгкая интеграция через API или виджет, подключение занимает минуты;
- наглядная статистика удовлетворённости в реальном времени;
- доказательная база для обоснования ресурсов на улучшение продукта;
- возможность отслеживать эффект от релизов и изменений (до/после).

Ценностные предложения для пользователей:
- упрощённый процесс оставления отзыва, один клик без громоздких форм;
- возможность быстро сообщить о проблеме или выразить (не)удовлетворённость;
- уверенность, что их мнение будет услышано и учтено.

## План работы

- Анализ требований и проектирование архитектуры (модель данных, API, виджеты).
- Разработка серверной части: CRUD для продуктов, генерация и управление API-ключами, эндпоинт приёма оценок, обработка и агрегация данных.
- Разработка встраиваемого виджета для веб-интерфейсов.
- Разработка клиентской части: страницы списка продуктов, статистики.
- Тестирование: функциональное, нагрузочное, безопасность.
- Пилотный запуск с несколькими продуктами и сбор обратной связи.

## Пользовательские сценарии

### Сценарий 1. Добавление нового продукта и получение API-ключа

Доступ: администратор ЦЭУ.
Предусловие: администратор авторизован, находится на главной странице управления продуктами.

Основной сценарий:
1. Администратор нажимает «Добавить сервис». Система открывает форму с полями: URL, выбор способа сбора оценок (API или виджет).
2. Администратор заполняет обязательные поля и нажимает «Создать». Система генерирует API-ключ, сохраняет сервис со статусом «Активен», показывает уведомление, API-ключ и код виджета (если выбран).
3. Администратор копирует ключ или код виджета и передаёт разработчикам.

Ожидаемый результат: продукт зарегистрирован, данные для интеграции получены.
Постусловие: продукт в списке, для него доступна страница статистики (пока пустая).

Альтернативные сценарии:
- URL уже зарегистрирован: ошибка «Сервис с таким названием уже зарегистрирован. Пожалуйста, укажите другой URL».
- Новый ключ для существующего продукта: кнопка «Сгенерировать ключ», старый ключ становится недействительным.
- Приостановка сбора оценок: статус «Неактивен», ключ перестаёт приниматься, данные сохраняются.

### Сценарий 2. Отправка оценки

Доступ: разработчик, пользователь сервиса.

Основной сценарий:
1. Разработчик настраивает продукт на отправку POST-запроса на эндпоинт `/api/ratings` с JSON: оценка от 1 до 5, идентификатор пользователя или сессии, комментарий (необязательно).
2. Пользователь оценивает продукт. Система проверяет API-ключ, структуру запроса, отсутствие оценки от этого пользователя в текущей сессии, сохраняет оценку.

Ожидаемый результат: оценка сохранена.
Постусловие: на странице статистики появляются новые данные.

Альтернативные сценарии:
- неверный API-ключ: 401 Unauthorized, попытка логируется;
- оценка вне диапазона 1–5: 400 Bad Request с описанием;
- более одной оценки в день (если включено ограничение): 429 Too Many Requests.

Примечание: в исходном ТЗ сценарий описывает экран «карточки занятия» и QR-код. Это текст из другого проекта, в ОКО его нет. Сценарий переписан по итогам встречи.

### Сценарий 3. Просмотр статистики продукта

Доступ: администратор ЦЭУ (в тексте ТЗ также владелец продукта).
Предусловие: продукт зарегистрирован и получает оценки.

Основной сценарий:
1. Владелец открывает главную страницу и видит список своих продуктов с краткой сводкой.
2. Владелец открывает карточку продукта. Система показывает: распределение оценок (1–5), NPS-подобный индекс (доля оценок 4–5), последние комментарии, фильтр по дате.
3. Владелец выбирает период, например «Неделя» → «Месяц». Графики перестраиваются.

Ожидаемый результат: владелец получил наглядную информацию о восприятии продукта.
Постусловие: администратор знает актуальное состояние качества и может принимать решения.

Альтернативный сценарий: если оценок нет, вместо диаграммы сообщение «Оценки по продукту пока отсутствуют. Ожидайте поступления данных».

## Команда

| Роль | Зона ответственности | Стек |
|---|---|---|
| Backend-разработчик | REST API, продукты и API-ключи, приём и обработка оценок, агрегация, оповещения, защита от накруток | Java (Spring Boot), PostgreSQL |
| Frontend-разработчик | веб-интерфейс (список продуктов, статистика), адаптивная вёрстка, графики | React |
| UI/UX дизайнер | дашборды, страницы статистики, формы, дизайн виджетов в разных стилях | Figma |
| QA-инженер | тест-планы, функциональное, интеграционное, нагрузочное тестирование, безопасность API, виджеты в разных браузерах | Postman |
| Аналитик | требования, документация API (OpenAPI), инструкции по интеграции, анализ данных | BPMN, SQL |

## Ожидаемый результат

- Развёрнутый веб-сервис для сбора и анализа оценок качества цифровых продуктов ТПУ.
- Единый стандарт интеграции через API с ключами для каждого продукта и готовые виджеты.
- Визуализация ключевых метрик (средняя оценка, распределение, динамика) с фильтрацией по периодам.
- Объективная база данных о восприятии цифровых продуктов для управленческих решений и отчётности.
- Повышение качества цифровых сервисов университета за счёт быстрой обратной связи.
