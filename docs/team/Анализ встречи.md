# Анализ встречи с заказчиком

Источник: «Analiz_vstrechi» из проекта OKO. Состав текста сохранён, даты и роли — как в исходнике (план на 14–27.10 относится к первому спринту и уже прошёл, актуальный план — в «План на неделю»).

## Главное

1. Заказчику важнее оценки пользователей, но на экране админа он хочет «лампочку» живой/мёртвый сервис и время отклика в миллисекундах. Эти данные берём через API команды мониторинга, сами ничего не замеряем.
2. Настоящая цель заказчика: после релиза быстро узнавать от пользователей о багах и разгрузить техподдержку. Звёзды — только инструмент.
3. Java остаётся. Kotlin заказчик не принял: поддерживать могут только Java.
4. Структура иерархическая: продукт, внутри него сервисы. Разработчики сами регистрируют свои продукты.

## Оговорка про запись

Транскрипция местами искажена. В протоколе такие места помечаются «подтвердите»:
- «афишка» почти везде означает «апишка», то есть API-ключ;
- «ЮРа или гид» — это URL или GUID;
- ссылка на документацию SSO неразборчива, попросить продублировать текстом;
- «админов три, разработчиков тридцать» звучит как оценка на глаз;
- Александр Сергеевич и Фадеев, вероятно, один человек, проверить;
- метки спикеров во второй половине записи перепутаны, это видно по смыслу.

## Что решили

| Тема | Что сказал заказчик | Уверенность |
|---|---|---|
| Приоритет | Оценки пользователей важнее технических метрик. Шкала любая: звёзды или числа. NPS 0–10 «можно взять как пример» | Чётко |
| Техметрики | Свой мониторинг не делаем. На экране: лампочка зелёная/красная и отклик в мс, данные из API мониторинга | Чётко, но нужны контакт и описание API |
| Структура | Продукт (например, личный кабинет), внутри него сервисы. Сервисов около 100, продуктов меньше | Понятно, но не ясно, на каком уровне ставят оценку |
| Релизы | Механику придумываем мы. Бизнес-цель: после релиза быстро получить оценки и разгрузить поддержку | Цель понятна, механика на нас |
| Что видит пользователь | Оценка, а при оценке ≤ 3 — поле «что не понравилось?». Идея верна, формулировки открыты | Идея принята, текст нет |
| Частота опроса | Ориентир раз в две недели, «чтобы не надоедало». Заказчик сам не уверен | Ориентир |
| Роли | Админ ЦЭУ видит всё. Разработчики сами заходят, добавляют продукт и видят свою часть. Роли «могут измениться» | Не окончательно |
| Авторизация | Нужна, через SSO ТПУ. Документация есть, доступ только после выдачи сервера | Принято, есть узкое место |
| Данные об оценщике | Хотя бы роль, «возраст максимум». Из SSO есть ID и ФИО, группа у студентов, роль не факт | Не ясно |
| Стек и виджет | Java. Виджет встраивают сами разработчики сервисов. Стеки разные: в основном PHP, возможно Django и другие | Чётко |
| Независимость | Если наш сервер упал, сервисы с виджетом не должны тормозить или ломаться (требование тимлида) | Чётко |
| Детализация | «Должно быть детально». Жёсткой связи метрик с бюджетом нет | Чётко |
| Организационное | Тестовый сервер ТПУ, позже перенос на серверы ЦЭУ. Дизайн по брендбуку ТПУ. Спринт две недели, созвон раз в спринт | Чётко |
| Ключ виджета | Вопрос про публичный и секретный ключи передан через Алину тимлиду, ответа нет | Ждём |

## Что это меняет

1. **Главный экран админа — дерево.** Продукт (лампочка), под ним сервисы (лампочки), рядом оценки и отклик. Модель строим как «продукт → много сервисов».
2. **«Простота» с поправкой.** Заказчик сказал «детально». Выход: сверху простая сводка для презентаций, под ней детали по кнопке.
3. **Лучшая демо-история.** «Вышел релиз, пользователь поставил 2 звезды и написал причину, разработчик увидел это в течение минут и увидел динамику до/после релиза».
4. **Релизы придумываем мы.** Предложение: метка релиза (дата, версия, описание); на графике вертикальная линия; сравнение «N дней до» и «N дней после».
5. **Оценки не анонимны, если брать данные из SSO.** Хранить ID и роль, не ФИО; владельцу показывать агрегаты и тексты без имён. Согласовать письменно.
6. **Нагрузка небольшая, но виджет грузится на каждой странице хоста.** Скрипт кэшируется, решение «показывать ли опрос» принимается по возможности в браузере.
7. **Зависимость от мониторинга.** Нужны контакт и описание API: только текущий статус или история, есть ли миллисекунды. Если истории нет, хранение делаем сами — новый объём.
8. **«Да» заказчика размашистое.** На вопросы про Grafana и детализацию ответы были не по теме. Всё важное закрепляем письменно.
9. **Сообщения о падении сервисов паркуем.** Лампочка из API мониторинга закрывает основной кейс «жив / не жив».

## Открытые вопросы (по приоритету)

Формулировать с вариантом по умолчанию: «если не возражаете, берём так».

**Срочно**
1. Контакт и описание API мониторинга. По умолчанию: работаем по макету формата данных.
2. Тестовый сервер и документация SSO. По умолчанию: заглушка входа, SSO подключим позже.
3. Оценка ставится на продукт или на каждый сервис? По умолчанию: на продукт, сервисы показывают статус.
4. Может ли разработчик сам зарегистрировать продукт, и кто подтверждает? По умолчанию: регистрация свободная, админ видит всё.
5. Пилотные сервисы: 2–3 штуки. На встрече не обсуждали, без реальных данных постер будет пустым.

**До презентации**
6. Ответ тимлида про ключи. Исходим из публичного идентификатора с проверкой сайта и секретного ключа для серверов.
7. Текст при низкой оценке: только поле или заготовленные причины плюс поле.
8. Какие данные из SSO храним и кто видит личность.
9. Лимит на оценки. По умолчанию: одна на пользователя на продукт в 14 дней, плюс опрос после релиза.
10. Механика релизов (предложение выше).
11. Нужны ли оповещения. По умолчанию: не в MVP.
12. Нужна ли Grafana или собственные страницы. По умолчанию: собственный фронтенд по ТЗ.

**Позже:** критерии успеха, данные help.tpu.ru для сравнения до/после, модерация комментариев, хранение данных, мобильные приложения.

## Риски

- Узкое место: сервер и SSO. Документация закрыта до выдачи сервера.
- Один бэкендер на всё: API, ключи, защита от накруток, агрегация, интеграция с мониторингом. Оповещения и расширенную защиту выносим за MVP.
- Заказчик не технический, формулировки «как работает» придумываем сами, просим подтверждения.
- Расплывчатое «детально»: на следующем созвоне показать вайрфрейм и спросить «так?».
