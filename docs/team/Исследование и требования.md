## 2. Дизайн: что на каких страницах

### Как считаем цифры (единые для всех страниц)

|Показатель|Как считается|
|---|---|
|Средняя оценка|Сумма оценок делить на их количество, один знак после запятой. Рядом стрелка ▲▼ к прошлому такому же периоду|
|Количество оценок (n)|Показываем всегда рядом с любой метрикой|
|Положительные / нейтральные / отрицательные|4–5, 3 и 1–2, в процентах от n|
|Индекс удовлетворённости|% положительных минус % отрицательных, от −100 до +100. В ТЗ он назван «NPS-подобный». В интерфейсе предлагаю назвать иначе, чтобы стейкхолдеры не путали его с настоящим NPS|
|Динамика|Средняя по дням (период до 30 дней) или по неделям (дольше)|
|До / после релиза|Средняя за 14 дней до метки и за 14 дней после, разница, n в каждом окне (предлагаю)|
|Мало данных|Если n < 20, значение серое с подписью «мало оценок (n=…)» (предлагаю)|
|Цвет оценки|≥ 4,0 зелёный, 3,0–3,9 жёлтый, ниже 3,0 красный (предлагаю)|
|Статус сервиса|Живой, не живой или «нет данных» (серый). Серый и красный нельзя путать, иначе недоступность нашего API мониторинга выглядит как падение сервиса|
|Отклик, мс|Последний и средний за период. Какие значения реально отдаёт API мониторинга, нужно узнать (см. вопросы в конце)|

### Страница 1. Вход

Кнопка «Войти через ТПУ». Пока SSO нет, простая форма-заглушка. Роль «админ ЦЭУ» назначается вручную.

### Страница 2. Сводная панель (главная)

Это то, что заказчик описал словами: дерево с лампочками.

- **Верх:** переключатель периода (7 / 30 / 90 дней / всё время), кнопка «+ Добавить продукт».
- **Карточки сводки:** продуктов, сервисов, оценок за период, средняя оценка по всем, сервисов «не живы» сейчас. Админ видит всё, разработчик только свои продукты.
- **Таблица-дерево.** Продукт раскрывается в список его сервисов. Колонки: лампочка, название, средняя оценка со стрелкой тренда, n, % положительных, отклик в мс, дата последнего релиза, владелец (только для админа).
- **Поиск и фильтры:** по названию, «только проблемные» (красные), сортировка по оценке и по n.
- Клик по строке открывает страницу продукта или сервиса.

### Страница 3. Страница продукта (и сервиса, шаблон тот же)

Шапка: название, URL, владелец, лампочка и отклик «сейчас», кнопка «Редактировать». Фильтры: период, сервис, версия или релиз. Внутри четыре вкладки.

**«Обзор»**

- Карточки: средняя оценка с трендом, n, % положительных и отрицательных, индекс удовлетворённости.
- График динамики средней оценки с вертикальными линиями релизов. В подсказке при наведении: дата, средняя, n.
- Гистограмма распределения оценок 1–5 (штуки и проценты).
- Блок «До / после релиза»: выбор релиза, две цифры и разница.
- Блок «Технические показатели»: статус, отклик в мс (текущий и средний), график отклика и % доступности, если API даёт историю.
- Мини-таблица «Сервисы внутри»: статус, оценка, n, отклик.

**«Отзывы».** Лента: дата, оценка, текст, сервис, версия, роль (студент или сотрудник, если SSO её отдаёт). Фильтры: только с текстом, только ≤3, период. ФИО и ID в ленте не показываем.

**«Релизы».** Список меток (дата, версия, название, изменение оценки до/после) и кнопка «Добавить релиз».

**«Интеграция».**

- Публичный ключ виджета и список разрешённых сайтов.
- Готовый код вставки с кнопкой «Копировать».
- Секретный ключ для серверной интеграции: показывается один раз, есть «Перевыпустить» и «Отозвать».
- Настройки: версия приложения, как часто спрашивать (14 дней по умолчанию), порог для текстового поля (≤3 по умолчанию).
- Предпросмотр виджета и ссылка на документацию.

### Страница 4. Форма «Добавить / изменить продукт»

Поля: название, описание, URL, владелец (по умолчанию текущий пользователь), список сервисов (название, URL, идентификатор в мониторинге). После сохранения сразу открывается вкладка «Интеграция». Если URL уже есть, ошибка «Продукт с таким URL уже зарегистрирован» (в ТЗ она написана про «название», это неточность).

### Виджет (живёт на чужих сайтах)

1. **Плашка:** «Как вам [название продукта]?», пять звёзд, ссылка «Не сейчас».
2. **Оценка 4–5:** «Спасибо!» и закрытие, текст не спрашиваем.
3. **Оценка ≤3:** поле «Что не понравилось? Что можно улучшить?», до 500 символов, кнопки «Отправить» и «Пропустить». Заказчик просил подумать над формулировкой вопроса, поэтому текст должен настраиваться, а не быть зашит.
4. **Ошибки:** если пользователь уже оценивал или сервер недоступен, виджет молча скрывается. Никаких ошибок на чужой странице.
5. **Как показывается:** раз в 14 дней, при смене версии показывается снова (предлагаю).
6. **Технические требования:** без зависимостей (обычный JS, работает на PHP, Django и любом другом стеке), стили изолированы, загрузка асинхронная, вес в пределах ~30 КБ (предлагаю), клавиатура и подписи для экранных дикторов. Два стиля, как в ТЗ: всплывающая карточка и встроенная строка.

## 3. Архитектура бэкенда

### Общая идея

**Один Spring Boot-сервис (модульный монолит) плюс PostgreSQL.** Не микросервисы: бэкендер один, времени шесть недель, и микросервисы тут просто ломают сроки. Фронтенд на React отдельно. Виджет отдельным лёгким скриптом. Всё запускается через docker-compose: nginx, приложение, база. Это легко перенести на сервер ЦЭУ.

### Модули внутри приложения

1. **Пользователи и вход.** Роли «админ» и «разработчик». SSO сделан за интерфейсом: сначала заглушка, потом подменяется на реальный вход, остальной код не меняется.
2. **Каталог.** Продукты, сервисы, владельцы, ключи.
3. **Приём оценок.** Отдельный быстрый и изолированный модуль. Он главный, потому что от него зависят другие сервисы.
4. **Статистика.** Не считать всё по сырым оценкам при каждом открытии. Хранить дневные агрегаты и обновлять их при приёме оценки.
5. **Релизы.** Метки и сравнение окон.
6. **Адаптер мониторинга.** Клиент API команды мониторинга за интерфейсом, пока с макетом данных. С таймаутами, кэшем и защитой от падения их API (при ошибке отдаём «нет данных»).

### Основные таблицы (черновик)

|Таблица|Ключевые поля|
|---|---|
|product|id, название, описание, URL, владелец, статус, дата создания|
|service|id, product_id, название, URL, идентификатор в мониторинге|
|api_credential|id, product_id, тип (публичный или секретный), хеш ключа, разрешённые сайты, дата отзыва|
|rating|id, product_id, service_id (может быть пусто), score, максимум шкалы (по умолчанию 5), текст, анонимизированный идентификатор оценившего, роль, путь страницы, версия, источник (виджет или API), дата|
|release|id, product_id, service_id (может быть пусто), версия, название, описание, дата релиза|
|rating_daily (агрегат)|product_id, service_id, дата, количество, сумма, количество оценок 1, 2, 3, 4, 5|

Оценка привязана к продукту, а service_id пустой или заполненный. Так любой ответ заказчика на вопрос «оценивают продукт или сервис» не ломает модель. Шкала хранится вместе с оценкой, чтобы NPS 0–10 можно было добавить позже без переделки. Секретный ключ хранится только в виде хеша, показывается один раз.

### Основные методы API (эндпоинты)

|Кто вызывает|Метод|Что делает|
|---|---|---|
|Виджет (публичный ключ)|`POST /api/v1/ratings`|Отправка оценки|
|Сервер продукта (секретный ключ)|`POST /api/v1/ratings`|То же из бэкенда или мобильного приложения|
|Интерфейс|`GET/POST/PUT/DELETE /api/products`, вложенные `/services`|Каталог|
|Интерфейс|`POST /api/products/{id}/keys`, перевыпуск, отзыв|Ключи|
|Интерфейс|`GET /api/overview`, `GET /api/products/{id}/stats`|Сводка и статистика|
|Интерфейс|`GET /api/products/{id}/ratings`|Лента отзывов|
|Интерфейс|`GET/POST /api/products/{id}/releases`, `GET .../releases/{rid}/compare`|Релизы и до/после|
|Интерфейс|`GET /api/monitoring/status`|Статус и отклик из чужого API|

Документацию в Swagger/OpenAPI Данил может получить автоматически из кода.

### Как идёт одна оценка

1. Скрипт виджета на чужой странице решает в браузере, показывать ли плашку. Для этого он смотрит в локальное хранилище, когда уже показывал. На сервер на каждой загрузке страницы он не ходит. Иначе наш трафик вырастет до уровня трафика всех хостов.
2. Пользователь ставит оценку, браузер шлёт запрос с публичным ключом.
3. Сервер проверяет ключ и сайт-источник, лимит запросов, длину и формат текста и дубликат (не было ли оценки от этого пользователя за последние 14 дней).
4. В одной транзакции сохраняет оценку и увеличивает дневной агрегат. Ответ 201.
5. Дашборд читает агрегаты и ленту отзывов.

### Защита от накрутки в MVP

- Два типа ключей: публичный (только запись оценок, привязан к списку сайтов, жёсткий лимит) и секретный (серверный).
- Лимиты по ключу и по оценившему. Лимит по IP делаем мягким, потому что в общежитиях и на вайфае весь корпус выходит с одного адреса.
- Идентификатор оценившего: если хост передаёт подписанный идентификатор, используем его, иначе анонимный из браузера. SSO для оценивающих добавим после ответа заказчика.
- Текст отзыва экранируем (защита от XSS в админке), длина ограничена, ФИО в базе не храним.

### Нефункциональные цели (предлагаю согласовать)

- Если наш сервер выключен, страница хоста работает как раньше (проверяется отдельным тестом).
- Виджет загружается асинхронно, таймаут запросов 2 секунды.
- Приём оценки укладывается в 300 мс на 50 запросах в секунду. Это с запасом: реальная нагрузка будет в десятки раз меньше.
- Страница статистики открывается за пару секунд на 100 тысячах оценок.

## 4. Что подтвердить, чтобы не переделывать

1. Что API мониторинга реально отдаёт: статус, отклик в мс, историю, доступность в процентах? Контакт и описание формата.
2. Оценка ставится на продукт целиком или на сервис внутри? Модель выдержит оба варианта, но дизайн страницы зависит от ответа.
3. Какие данные об оценившем из SSO можно хранить и кто видит личность.
4. Пилотные сервисы: без них на постере 25.12 не будет реальных данных.
5. Ответ тимлида про публичный и секретный ключи. Я заложил это решение.

## 5. Порядок работ

- **Спринт 1 (до 27.10):** вход с заглушкой, каталог (создание продукта и ключей), приём оценок через API, простая таблица оценок. Дизайн виджета и страниц 2–3 утверждён.
- **Спринт 2 (до 10.11):** виджет на тестовой странице, статистика продукта (метрики и графики), адаптер мониторинга по макету, дерево на сводной панели.
- **Спринт 3 (до 22.11):** метки релизов и до/после, лента отзывов, нагрузочные и защитные тесты, демо-данные и сценарий показа к 23.11.

Историю для демо подбирай так: «релиз, плохая оценка с причиной, разработчик увидел это в панели, график до/после». Она закрывает главное, ради чего заказчик затеял проект.
