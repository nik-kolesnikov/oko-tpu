# ОКО ТПУ: архитектура

Документ фиксирует архитектуру MVP. Пункты, которые ещё не согласованы с заказчиком или ТПУ, помечены как «открыто».

## 1. Общая схема

```
 Сайт ТПУ (PHP / Django / Java / React)        Браузер сотрудника ЦЭУ / разработчика
 ┌──────────────────────────────┐              ┌──────────────────────────────┐
 │ страница + <script loader.js>│              │ React SPA (панель, статистика)│
 │   └─ iframe виджета          │              └──────────────┬───────────────┘
 └──────────────┬───────────────┘                             │ HTTPS
                │ HTTPS, публичный ключ                       │ /api/*
                ▼                                             ▼
        ┌──────────────────────── nginx ─────────────────────────┐
        │  статика: виджет, iframe-страница, SPA                  │
        │  /api/*  → Spring Boot                                  │
        └──────────────────────────────┬─────────────────────────┘
                                       ▼
        ┌──────────────── Spring Boot (модульный монолит) ────────┐
        │ auth  catalog  ratings  stats  releases  monitoring     │
        └────────┬───────────────┬──────────────────┬─────────────┘
                 ▼               ▼                  ▼
          PostgreSQL       SSO ТПУ (oauth.tpu.ru)   API мониторинга
                                                  (сейчас заглушка)
```

Сервер продукта (мобильное приложение, бот, CI) ходит в `/api/*` напрямую с секретным ключом. Он не проходит через виджет.

## 2. Компоненты

| Компонент | Что делает | Технологии |
|---|---|---|
| nginx | Раздаёт статику (виджет, SPA), проксирует `/api/*`, терминирует HTTPS, отдаёт 503 при недоступном приложении | nginx |
| Веб-интерфейс ОКО | Дерево продуктов, карточки, статистика, релизы, интеграция | React, сборка в статику |
| Виджет | `loader.js` на чужом сайте: кнопка, плашка, iframe. Внутри iframe — форма оценки | Чистый JS без зависимостей, отдельная маленькая страница для iframe |
| Backend | Вся логика, API, права, приём оценок, агрегаты | Spring Boot 3, Spring Security, Spring Data JPA, Flyway |
| База | Продукты, сервисы, ключи, оценки, агрегаты, релизы | PostgreSQL |
| Адаптер мониторинга | Опрос API команды мониторинга по расписанию, кэш, защита от их сбоев | Модуль внутри backend, за интерфейсом `MonitoringSource` |
| Адаптер SSO | Обмен code на токен, `/user`, заглушка для разработки | Модуль внутри backend, за интерфейсом `IdentityProvider` |

Виджет не тянет React. Это принципиально: он работает на сайтах с любым стеком и не должен конфликтовать с их библиотеками.

## 3. Модули backend

Один артефакт, пакеты по модулям. Модули общаются через сервисы, а не через чужие таблицы.

1. **auth.** Вход, сессия ОКО, роли (админ ЦЭУ по списку в конфигурации, остальные — владельцы через связь с продуктом). Проверка прав: «админ или владелец этого продукта».
2. **catalog.** Продукты, сервисы, владельцы, ключи (выдача, перевыпуск, отзыв, список разрешённых сайтов).
3. **ratings.** Приём оценок. Самый важный модуль: изолированный, быстрый, с лимитами. От него зависит всё остальное.
4. **stats.** Чтение агрегатов, расчёт средней, индекса, трендов, сравнения до/после. Без обращения к сырым оценкам для графиков.
5. **releases.** Метки релизов, окна сравнения, пересечения окон.
6. **monitoring.** Приём Push-событий мониторинга в постоянный журнал, обновление последнего статуса
   и преобразование в «жив / не жив / нет данных». Защищённый Pull API для первоначальной
   и периодической сверки добавляется после реализации его командой мониторинга.

Ключевое правило: `ratings` не знает про `monitoring`, `stats` не пишет в `ratings`. Агрегаты обновляет сам модуль `ratings` в той же транзакции, что и сохранение оценки.

## 4. Потоки данных

### 4.1. Оценка через виджет

1. Скрипт `loader.js` подключается асинхронно, после загрузки страницы.
2. Скрипт проверяет в `localStorage`, показывал ли он уже плашку. Если да и не прошло 14 дней, он молчит. На сервер за этим не ходит.
3. `loader.js` вставляет iframe `/api/v1/widget/frame?key=…`. Страницу iframe отдаёт backend с `Content-Security-Policy: frame-ancestors <разрешённые сайты продукта>`, поэтому на чужом сайте браузер iframe не покажет. Идентификатор оценившего `loader.js` передаёт в iframe через `postMessage`.
4. Пользователь ставит звёзды. Если оценка ≤3, появляется поле текста.
5. iframe шлёт `POST /api/v1/widget/ratings` с публичным ключом, оценкой, текстом и идентификатором оценившего. iframe живёт на домене ОКО, поэтому `Origin` запроса — всегда origin ОКО (`OKO_PUBLIC_ORIGIN`), а не сайт продукта.
6. Backend проверяет: ключ существует и активен, продукт активен, `Origin` равен origin ОКО, лимиты, длина и формат текста, сервис принадлежит продукту, дубликат за 14 дней. Сайты продукта здесь не сверяются: это уже сделал браузер по `frame-ancestors` на шаге 3.
7. В одной транзакции: запись в `rating`, увеличение `rating_daily` за день в часовом поясе Томска. Ответ `201`.
8. Ошибка на любом шаге: виджет молча скрывается, без сообщения на чужой странице.

### 4.2. Оценка с сервера продукта

Тот же приём, но `POST /api/v1/ratings` с секретным ключом в заголовке. Лимиты мягче, а идентификатор оценившего передаёт сам продукт.

### 4.3. Статистика

Панель читает `rating_daily` и `rating`. Сырые оценки читаются только для ленты отзывов и для вычисления дубликатов. Для периодов до 30 дней точки графика — по дням, дольше — по неделям.

Округление и правила подсчёта: средняя с одним знаком, n рядом с каждой метрикой, серый при n < 20.

### 4.4. Мониторинг

Не запрос на каждое открытие страницы: мониторинг отправляет `POST /api/v1/status/events`
при смене статуса и по HEARTBEAT. ОКО проверяет Bearer-токен, сохраняет событие
в `monitoring_event`, затем обновляет `service_status` только для более новой проверки.
`service_status_log` получает записи о смене состояния. По `resource_id` событие
сопоставляется с уникальным `service.monitoring_ref`; неизвестный ресурс сохраняется
и привязывается позднее. Если последняя проверка старше 5 минут, статус становится
«нет данных» (серый). Сбой мониторинга не прерывает работу панели.

После появления у команды мониторинга защищённого `GET /api/v1/statuses`
будет добавлена первичная и периодическая сверка. Подробности и текущий статус
этого этапа — в `docs/MONITORING_INTEGRATION.md`.

Панель и виджет читают только нашу таблицу. Мониторинг не может «положить» наш интерфейс.

Лампочка продукта собирается из его активных сервисов (контракт, `ProductHealthStatus`): все известные упали — красная, есть и упавшие, и рабочие — жёлтая (`degraded`), все работают — зелёная, иначе серая. Известное падение важнее нехватки данных.

### 4.5. Релизы и сравнение до/после

Метка релиза создаётся владельцем или админом. Окно «до» — 14 дней перед днём релиза, «после» — 14 дней начиная с дня релиза. Окна обрезаются с двух сторон: «до» — по дате предыдущего релиза того же продукта (или сервиса), «после» — по дате следующего. Иначе при двух релизах в одну неделю окна пересекутся, и эффект одного релиза припишется другому.

## 5. Модель данных

| Таблица | Ключевые поля | Примечание |
|---|---|---|
| `app_user` | id, login, full_name, email, created_at | Только для владельцев и админов. Оценивающих здесь нет |
| `product` | id, name, description, url, status, created_at | Статусы: активен, приостановлен, удалён (архив) |
| `product_owner` | product_id, user_id | Владельцев несколько, минимум один |
| `service` | id, product_id, name, url, monitoring_ref | `monitoring_ref` — идентификатор в их системе |
| `api_key` | id, product_id, type (public/secret), key_hash, key_prefix, created_at, revoked_at | Оба типа ключа только в виде хэша; полный ключ показывается при выпуске и перевыпуске |
| `allowed_origin` | id, product_id, origin | Для `frame-ancestors` страницы iframe |
| `rating` | id, product_id, service_id (nullable), score, scale_max, comment, rater_hash, role, page_path, version, source, created_at (timestamptz) | `rater_hash` — не ID и не ФИО |
| `rating_daily` | product_id, service_id, day (date, Томск), cnt, sum_score, c1, c2, c3, c4, c5 | Агрегат, обновляется в транзакции |
| `release_mark` | id, product_id, service_id (nullable), version, title, description, released_at | |
| `service_status` | service_id, status, response_ms, checked_at | Последний статус, заполняет модуль `monitoring` |
| `service_status_log` | service_id, status, response_ms, checked_at | История проверок для процента доступности |
| `monitoring_event` | event_id, resource_id, payload, checked_at, event_type, service_id | Журнал событий мониторинга: повтор не создаёт дубль, неизвестный ресурс привязывается позже |
| `widget_settings` | product_id, question, ask_interval_days, comment_threshold, position | |

Агрегат `rating_daily` — главная страховка производительности. Графики строятся по нему, а не по сырым оценкам.

## 6. Роли

- **Админ ЦЭУ** задаётся списком логинов в конфигурации (`OKO_ADMIN_LOGINS`). Пока SSO не подключён, можно включить вход одного админа по паролю (`OKO_ADMIN_LOGIN`, `OKO_ADMIN_PASSWORD`); по умолчанию он выключен. Видит все продукты, может завести продукт за команду, приостановить, удалить (данные уходят в архив), перевыпустить ключ любого продукта.
- **Владелец продукта** — связь «пользователь ↔ продукт», не отдельная роль. Регистрирует продукт и сервисы, настраивает виджет, управляет ключами, отмечает релизы, смотрит статистику и отзывы своих продуктов, добавляет других владельцев. Минимум один владелец всегда.
- **Оценивающий** — не пользователь системы, отдельной роли нет.

Открыто: регистрация продукта свободная (дефолт) или только по подтверждению админа.

## 7. Идентичность и защита от накрутки

**Решено:**
- публичный ключ для виджета и секретный для серверов (ответ тимлида не получен, исходим из этого);
- лимит «одна оценка от человека за 14 дней»;
- личность оценивающего не видит никто, включая админа.

**Открыто:** в этом документе SSO для оценивающих отложен, а при разговоре с ТПУ договорились, что SSO закрывает накрутки. Нужно решить до старта спринта 2.

**Предлагаемый вариант:**
- идентификатор оценившего = HMAC от `lichnost_id` с секретом ОКО. Личность не хранится, но один человек даёт одинаковый хэш;
- до подключения SSO идентификатор анонимный (cookie браузера). В интерфейсе честно написано, что оценки анонимные и возможны повторы;
- когда SSO заработает, модуль `auth` подменяет источник идентификатора, остальной код не меняется.

Остальные меры: лимит запросов на публичный ключ, мягкий лимит на IP (в общежитиях много людей за одним адресом), `frame-ancestors` на странице iframe и проверка, что оценка пришла из нашего iframe (`Origin`), экранирование текста при выводе, ограничение длины текста.

## 8. Надёжность и изоляция

- **Наш сервер упал.** Страница хоста не зависает: скрипт асинхронный, запросы с таймаутом 2 секунды, при ошибке виджет скрывается.
- **Сервер продукта шлёт оценки.** Короткий таймаут, отправка в фоне, ошибка логируется и не влияет на ответ пользователю.
- **API мониторинга недоступен.** Статус «нет данных», панель работает.
- **База недоступна.** Приём оценок отвечает 503, фронтенд показывает понятное сообщение.
- **Свой мониторинг.** Эндпоинт `/actuator/health` и внешний пинг сервера.

## 9. Инфраструктура и эксплуатация

**Сервер.** Один сервер на всё: работа, тесты, демо. Минимум 2 vCPU, 4 ГБ RAM, 50 ГБ SSD; комфортно 2–4 vCPU, 6–8 ГБ, 80 ГБ. Отдельного тестового сервера не будет.

**Окружения:**
- `prod-like` (он же демо и стенд приёмки) — на сервере, только согласованные версии;
- `dev` — на ноутбуках разработчиков: локальный PostgreSQL в Docker, заглушка SSO.

**Запуск.** docker-compose с тремя контейнерами (nginx, backend, PostgreSQL). Если Docker на сервере запрещён, Spring Boot запускается jar-файлом через systemd, PostgreSQL ставится напрямую. Открыто: подтвердить у ЦЭУ.

**Память на сервере (ориентир):** JVM heap 1–2 ГБ, `shared_buffers` PostgreSQL 256–512 МБ, nginx, ОС и Docker 0,5–1 ГБ. Swap 1–2 ГБ как страховка.

**Конфиги и секреты.** Переменные окружения. Секреты, включая `client_secret`, не попадают в репозиторий. Запрос на обмен code на токен (с секретом в адресе) не логируется целиком.

**Миграции.** Flyway. Схема меняется только через миграции.

**CI.** Сборка, юнит- и интеграционные тесты (Testcontainers) и сборка образов — на GitHub Actions или ноутбуках, не на сервере. На сервер приходит готовый образ.

**Бэкапы.** Ежедневный дамп PostgreSQL, хранение 14 дней. Копия обязательно вне основного диска (другой носитель или облачное хранилище). Открыто: что доступно.

**Логи.** Структурированные, без персональных данных и без текста оценок. Ротация по размеру (например, 100 МБ на файл, 5 файлов).

**Мониторинг сервера.** Внешний пинг с уведомлением на почту. Node Exporter откладываем, пока хватает памяти.

**Замораживание версии.** За неделю до демо (23.11) и постера (25.12) версия на сервере фиксируется, эксперименты отменяются.

## 10. Тесты

- **Приём оценки:** корректный запрос, неверный ключ, чужой `Origin`, дубликат за 14 дней, текст сверх лимита.
- **Агрегаты:** сумма по `rating` и `rating_daily` совпадает (отдельный тест на сверку).
- **Права:** владелец не видит чужой продукт, админ видит всё.
- **Отказ зависимостей:** мониторинг выключен, SSO выключен, база недоступна.
- **Виджет:** сервер выключен, страница хоста загружается нормально (ручной и автоматический сценарий).
- **Окна до/после** при двух близких релизах.
- **Нагрузка:** локально, на ноутбуке, с оговоркой, что цифры ориентировочные. Требование 50 запросов в секунду проверяется и помечается как неподтверждённое на проде.

## 11. Открытые вопросы

1. **Идентичность оценивающих до SSO:** анонимный cookie с оговоркой или ждём SSO.
2. **Удаление продукта:** только админ, данные уходят в архив. Подтвердить.
3. **Порог «нет данных»:** 5 минут. Подтвердить.
4. **Срок хранения сырых оценок.** Предложено не удалять, пока не решено с заказчиком.
5. **Docker и доступ к бэкапам** на сервере ЦЭУ.
6. **Что реально готово из спринта 1** (срок был 27.10) и как сдвигается спринт 2.
