# ОКО ТПУ — оценка качества цифровых продуктов

Сервис, где владельцы продуктов ТПУ (сайты, личные кабинеты, приложения) получают оценки пользователей: через виджет на своём сайте и через API. Владелец видит статистику по продукту и сервисам, отмечает релизы и смотрит эффект до/после. ЦЭУ видит сводку по всем продуктам с лампочками состояния.

MVP: неделя работ (3–10 ноября). К 7 ноября готовы основа и виджет, после этого — интеграция с API мониторинга и остальной объём. Точный план — в `docs/team/План на неделю.md`.

## Источник правды

Читай нужный раздел, а не всё подряд. При расхождении порядок такой:

1. `contracts/oko-openapi.yaml` — форма обмена между панелью, виджетом, серверами продуктов и backend. Backend реализует именно её. Владелец — Николай.
2. `docs/db.md` — таблицы и ограничения. Схема меняется только миграциями Flyway. Владелец — Данил.
3. `docs/architecture.md` — модули, потоки данных, инфраструктура. Владелец — Данил.
4. Макеты в Figma — внешний вид и сценарии экранов. Владелец — Максим. Не реализуй экран по памяти: открой макет или спроси.
5. ТЗ и протоколы встреч — `docs/team/`. Требования заказчика.

Если документы расходятся, не выбирай молча, какой прав. Сообщи о расхождении и остановись: решает аналитик (Николай), а не Claude.

## Решения команды

Это решения, а не предложения. Меняются только через Алину и Николая, с записью в протокол.

**Модель данных и подсчёт**
- Оценка всегда привязана к продукту. Сервис необязателен (`service_id` nullable).
- Шкала 1–5. Шкала хранится вместе с оценкой (`scale_max`), чтобы NPS 0–10 можно было добавить позже.
- Средняя — один знак после запятой. Рядом всегда показываем n.
- Индекс удовлетворённости = доля оценок 4–5 минус доля оценок 1–2, в процентах от n, диапазон −100…+100. Название «NPS» в интерфейсе не используем.
- Если n < 20, значение серое с подписью «мало оценок (n=…)».
- Периоды — календарные дни по Томску (`Asia/Tomsk`).
- Дашборд и статистика читают агрегат `rating_daily`, а не сырые оценки.

**Релизы и до/после**
- Окно «до» — 14 дней перед днём релиза. Оно обрезается по дате предыдущего релиза того же продукта (или сервиса).
- Окно «после» — 14 дней, начиная с дня релиза. Оно обрезается по дате следующего релиза.
- Обрезка с двух сторон нужна, иначе при двух релизах в одну неделю окна пересекаются, и эффект одного релиза приписывается другому.

**Лампочка продукта**
- зелёная — все активные сервисы работают;
- жёлтая — часть сервисов не отвечает;
- красная — не отвечает ни один;
- серая — нет данных или они старше 5 минут.
- Серая и красная не путаются: недоступность нашего API мониторинга не должна выглядеть как падение сервиса.
- ТЗ упоминает только зелёную и красную. Жёлтое и серое согласуем с заказчиком до демо.

**Владельцы и роли**
- Роли две: админ ЦЭУ и владелец продукта. Роль «разработчик» из ранних документов не используем.
- Админы задаются списком в конфигурации, в БД не хранятся.
- Владелец — связь «пользователь ↔ продукт». У продукта минимум один владелец.
- Добавить владельца можно только того, кто уже входил в ОКО (MVP).
- Архивировать продукт может только админ. Владелец может только приостановить.
- Личность оценившего не видит никто, включая админа.

**Оценивающие (до SSO для оценивающих)**
- Идентификатор оценившего — анонимный UUID браузера (`raterId`). Сервер хранит только HMAC от него.
- Лимит «одна оценка от человека за 14 дней» — мягкий. Честно пишем в интерфейсе, что оценки анонимные и возможны повторы.
- Лимит по IP — мягкий, в общежитиях много людей за одним адресом.

**Ключи и виджет**
- При регистрации продукта ключи не выпускаются. Владелец выпускает их кнопками на вкладке «Интеграция».
- Полный ключ, и публичный, и секретный, показывается только при выпуске и перевыпуске. Потом виден только префикс.
- Потерянный ключ не восстанавливается: его перевыпускают и заменяют код вставки на всех сайтах. Публичный ключ не секрет, но и хранить его открыто незачем.
- Страницу iframe отдаёт backend с `Content-Security-Policy: frame-ancestors` по списку разрешённых сайтов продукта.

**Ошибки и API**
- Префикс `/api/v1`, JSON, поля в `camelCase`. В БД — `snake_case`.
- Формат ошибок — плоский, как в спецификации: `code`, `message`, `details` на верхнем уровне. Не вкладывай их в объект `error`: это формат другого проекта.
- Коды ошибок — только из спецификации. Новый код — PR в спецификацию.

## Правила работы с Claude

- Работай только в своей папке. Соседние папки читай, но не меняй.
- `contracts/` не меняй. Нужна правка — опиши её в PR: что меняется, зачем, ломает ли совместимость. Аппрувят аналитик и затронутая сторона.
- Ломающие изменения (переименование, смена типа, обязательность поля) до заморозки v1.0 — только с уведомлением команды. После — только по общему согласию.
- Не отходи от спецификации молча. Если решение из неё неудобно — сообщи в чат и предложи правку спецификации.
- Новая логика — с тестом. Перед словом «готово» запусти тесты своей папки и сверь ответы с `contracts/oko-openapi.yaml`.
- Большое изменение (больше одного модуля, новая таблица, новый эндпоинт) — сначала план, код потом.
- Не читай `.env`, `secrets/`, реальные выгрузки с персональными данными.
- Для примеров и фикстур используй выдуманные данные: логины, ФИО, email.
- Git: не делай `push --force`, `rebase` общих веток и удаление веток без явной просьбы.
- Коммиты делает человек, который прочитал код. Claude указывается строкой `Co-Authored-By`.

## Безопасность (общее)

- Ключи, `client_secret`, HMAC-секрет, пароли — только в переменных окружения. Не в репозиторий, не в чат, не в логи.
- Персональные данные (ФИО, email, `lichnost_id`) не возвращаются тем, кто не владелец продукта или админ. В логах не печатаются.
- Тексты оценок — пользовательский ввод. Не выполняются, не вставляются как HTML, экранируются при выводе.
- Заглушка входа (dev-режим SSO) включается только профилем `dev`. В `prod` её быть не должно, и это проверяется тестом.
- Вход админа по паролю (`OKO_ADMIN_LOGIN`, `OKO_ADMIN_PASSWORD`) — временный, пока нет SSO. Это не заглушка: один логин, пароль не короче 16 символов, лимит попыток. По умолчанию выключен.
- Персональные данные в тексте отзывов возможны: пользователи могут написать ФИО или телефон. Модерации в MVP нет. Текст виден только владельцу продукта и админу.
